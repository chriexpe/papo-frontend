# papo-api

Stateless Papo REST and gateway transport. Each `RestClient` owns an in-memory
cookie jar for one server. Redirects and automatic retries are disabled. The
SDK owns persistence, token refresh decisions, reconnects and generations.
Errors discard transport diagnostics and format only static descriptions and
HTTP statuses; problem documents remain available as typed data. Wire records
and live payloads deliberately do not implement `Debug`.

`protocol/backend-commit` pins the public `chriexpe/papo-backend` revision.
Generated records preserve OpenAPI optionality and nullability, and keep
timestamps as exact strings. IDs are opaque wire strings (webhook messages may
carry an empty author ID); UUID validation occurs when a consumer needs an
identity. Use `Message::cursor()` to carry the exact `created_at` and `id` pair
into either direction of `HistoryQuery`.

Both drift checks require a backend Git checkout whose HEAD matches the pin.
They read its OpenAPI and Go declarations directly and compare generated wire
records and gateway dispatch with the committed Rust. A committed wire file
that is no longer generated fails the check and is not deleted automatically.
The PostgreSQL CI job runs both checks. Set `PAPO_BACKEND` to that checkout when
running the SDK gate; without it, the gate explicitly reports that the
backend-dependent checks were not run. The Python build tooling needs PyYAML 6.0.3. After reviewing a contract
change, regenerate with `python3 scripts/papo-api-contract.py --backend <checkout> --write`
and `python3 scripts/papo-api-events.py --backend <checkout> --write`.

`Gateway::next()` must be polled continuously. It sends application heartbeats
at 25-second intervals, requires acknowledgement by the next heartbeat, and
services RFC 6455 pings. It creates no task and no reconnect policy. Unknown
events preserve their JSON; malformed known events return typed errors. A
normal close has no authentication meaning: the pinned backend also uses it
when revoking connections.

Run the example with `cargo run -p papo-api --example live_events`. Supply
`PAPO_ADDRESS`, `PAPO_USERNAME`, and `PAPO_PASSWORD` through the environment;
missing values are read as stdin lines in that order. Private servers may use
`PAPO_SERVER_PASSWORD`. Nothing accepts credentials or addresses as arguments.
Output contains static event kinds and parsed UUIDs only. `PAPO_EVENT_LIMIT`
optionally bounds a smoke run. `PAPO_LOOPBACK_HTTP=1` explicitly enables Secure
cookies over HTTP for literal loopback hosts only; production clients use
normal cookie security rules.

The Linux PostgreSQL job builds both the unmodified backend executable and a
small harness using that revision's production handlers, middleware, gateway,
and migrations. The harness binds IPv4 loopback on an assigned port, generates
signing secrets in memory, seeds seven bodyless messages (five with an identical
microsecond timestamp), and requires only `DATABASE_URL` from its environment.
The database must also use a literal loopback host and be disposable. A separate
proof password is generated by CI and passed only through environment variables.
Backend logging is discarded. The proof tests page sizes 1, 2, 3, 7 and 8 in
both directions, terminal pages, interior direction reversal and verbatim cursor
strings, then runs the live example. Run it with
`python3 scripts/papo-backend-proof.py --backend <pinned-checkout>` after setting
`DATABASE_URL` and an ephemeral `PAPO_PROOF_PASSWORD` satisfying backend policy.
The harness uses a fresh database; it is not an upgrade or migration test.
